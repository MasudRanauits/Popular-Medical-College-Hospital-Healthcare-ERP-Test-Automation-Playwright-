BUG-001 — Patient Registration list opens empty because the date filter defaults to today

Module / page Registration > Patient Registration (/hospital/newregistration)
Severity / Priority Medium / P2
Status open — reproduced on both attempts of the 03 Oct run. Still present on 05 Oct; TC_ADM_002 passed that day only because it now widens the range itself (AUT-001, section 6).
Found by TC_ADM_002 — tests/regression/admission.regression.spec.ts:63
Reproducibility Deterministic. Any day before the first patient of the day is registered — in the 03 Oct run, both attempts, 08:04 UTC.

Steps to reproduce

  1. Sign in as Administrator.
  2. Click the REGISTRATION tile on the module launcher.
  3. Click PATIENT REGISTRATION in the left drawer.
  4. Look at the grid without touching the date filter.

Expected result

The patient list opens on a range that shows work in progress — the recent registrations — so a user arriving at the page can find and open a patient record without first reaching for the date pickers.

Actual result

Show From and Show To are both set to today (10/3/2026), so the grid shows only patients registered today. Before the day's first registration that is nobody: the headers render, the body is empty, and the pager reads 0-0 of 0. The page gives no indication that a filter is responsible — there is no empty-state message and no hint that widening the range would bring rows back.

Evidence

  • Playwright trace — assets/failures/TC_ADM_002/trace-2.zip. Open with npx playwright show-trace docs/assets/failures/TC_ADM_002/trace-2.zip for the DOM snapshot, network log and console at each step.
  • Page snapshot — assets/failures/TC_ADM_002/error-context-1.md and error-context-2.md. The accessibility tree at the moment of failure, including the empty row groups and the 0-0 of 0 pager.

Error as the run reported it

TimeoutError: locator.innerText: Timeout 30000ms exceeded.
Call log:
  - waiting for locator('table.mud-table-root')
      .locator('tbody tr').first().locator('td').nth(1)

  at tests/regression/admission.regression.spec.ts:32
     const uhid = (await registrationPage.rows.first()
                     .locator('td').nth(1).innerText()).trim();

Analysis

The grid did not fail to load — it loaded correctly and returned nothing, because the filter it loaded with asks for one day. The run itself proves the filter is the cause rather than the data: TC_REG_004, which asserts the same grid has at least one row, passed in the same run. It runs after TC_FLOW_001, which registers a patient — so by the time TC_REG_004 looked, there was one registration dated today and the same default filter returned it. TC_ADM_002 ran before that, and saw an empty day.

Suggested fix

  • Default Show From to a range that covers recent work — the last 7 or 30 days — rather than today, with Show To staying at today.
  • Failing that, render an empty state in the grid that names the filter: "No patients registered between 10/3/2026 and 10/3/2026. Widen the date range to see earlier registrations."

BUG-002 — Advance payment taken in the admission wizard never reaches the Advance Dashboard

Module / page Hospital > New Admission (/hospital/patientadmission) → Hospital > Advance Dashboard
Severity / Priority High / P1 — money is collected at the counter and does not appear against the admission
Status open — needs confirmation from the module owners
Found by TC_FLOW_001 — tests/regression/admission.regression.spec.ts:121
Reproducibility Every run of the end-to-end flow so far.

Steps to reproduce

  1. Sign in as Administrator and register a patient.
  2. Open New Admission and search the new UHID.
  3. Fill the Contact Person tab.
  4. On Advance Payment, enter all three: card VISA / EBL POS 1000, bKash 2000, cash 3000.
  5. Confirm the Total: panel reads 6000.
  6. Complete Admission Detail and press Create Patient Admission.
  7. Open Hospital > Advance Dashboard and look for the admission.

Expected result

The 6000 taken at admission is recorded against the new admission and shows on the Advance Dashboard, so the billing desk can see what the patient has already paid.

Actual result

The admission is created correctly — it appears on Patient Dashboard For Billing Dept with the right bed, ward, mobile and blood group — but the Advance Dashboard carries no row for it. The wizard's own Total panel had summed the three amounts to 6000 immediately before the submit, so the figures were accepted by the form and lost somewhere between the submit and the advance ledger.

Evidence

  • No screenshot: the run that produced this observation predates the evidence collector, and TC_FLOW_001 passes, so Playwright captures nothing for a passing test.
  • The observation is recorded in the test itself, at tests/regression/admission.regression.spec.ts:189, as the reason the advance total is deliberately not asserted after the submit.
  • The pre-submit total is asserted (Total: 6000), so every passing run is standing evidence that the amounts reached the form.

Open question for the module owners

It is not yet established whether this is a defect or a missing step: Advance Collection is its own page, and it may be that the wizard's Advance Payment tab only records an intent and the money has to be receipted separately. The answer decides whether this is a code fix or a documentation and training issue — and either way the wizard should not present a Total that then goes nowhere.

Suggested fix

  • If the wizard is meant to post the advance: fix the posting and add the Advance Dashboard assertion to TC_FLOW_001 so the fix stays fixed.
  • If it is not: remove or relabel the Advance Payment tab so it does not read as money taken, and state where the receipt is actually raised.

BUG-003 — Brute-force throttle answers every request from the IP with HTTP 429, not just login attempts

Module / page Authentication — affects the whole application
Severity / Priority Medium / P2
Status open
Found by The negative login cases (TC_LOGIN_003–007), whose after-effects reached unrelated pages.
Reproducibility Consistent, after roughly seven failed logins from one address.

Steps to reproduce

  1. From one IP address, attempt to log in with a wrong password about seven times.
  2. From the same IP, on a different machine or browser, request any page — including one an already-signed-in user is working on.

Expected result

Throttling protects the sign-in endpoint and the account being attacked. Other users on the same network, and other routes, keep working.

Actual result

The host answers every request from that address with HTTP 429 and Retry-After: 60. Measured, it clears in about ten seconds rather than the sixty advertised. During the cool-off a Blazor page load does not degrade gracefully: the circuit never starts, so the page renders as dead chrome rather than showing a "too many attempts, try again shortly" message.

Why it matters beyond the test suite

A hospital floor is behind one NAT address. One person mistyping their password several times locks out everyone on that floor for the cool-off — reception, billing and the wards alike — with no message explaining why the ERP has stopped responding.

Evidence

  • Worked around in utils/helpers.ts — gotoTolerant() and reloadTolerant() retry past the 429, and their comments record the measured behaviour.
  • reloadTolerant() also documents a second symptom: a plain reload during the cool-off does not surface the 429 at all, it throws net::ERR_HTTP_RESPONSE_CODE_FAILURE.

Suggested fix

  • Scope the throttle to the sign-in endpoint and the account being attempted, not to every route from the IP.
  • Make Retry-After truthful — advertise the ten seconds actually enforced.
  • Serve a readable 429 page instead of letting the Blazor circuit fail silently.

BUG-004 — Patient Registration grid can take over 30 seconds to render its first row

Module / page Registration > Patient Registration (/hospital/newregistration)
Severity / Priority Medium / P2
Status open — intermittent — 33.8 s on 03 Oct, 10.3 s on 05 Oct. Slow either way, but not reproducibly over 30 s; see Actual result.
Found by TC_REG_004 — tests/regression/registration.regression.spec.ts:71

Steps to reproduce

  1. Sign in as Administrator.
  2. Open Registration > Patient Registration.
  3. Time how long it takes for the first row to appear, on a range that has data.

Expected result

A single page of ten rows renders in a couple of seconds, like every other page in the suite.

Actual result

TC_REG_004 took 33.8 seconds in the 03 Oct run, against a suite median of about 2 seconds. It does nothing but open the page, read six column headers and wait for one row — the time is the grid. The same slowness is why the project raises Playwright's default timeouts across the board: 90 s per test, 30 s per action, 45 s per navigation.

Re-measured on 05 Oct: 10.3 seconds. Three times faster, and still four to five times every other case on the same page in the same session. So the page is reliably slow and sometimes very slow, which points at load on the host or on the query rather than at a fixed cost. The defect stands, with the headline figure read as a worst case rather than as typical.

Evidence

  • Run timings in docs/assets/failures/manifest.json, and in the HTML report under playwright-report/. Comparison, 03 Oct run, same session: TC_REG_003 (same page, no row wait) 2.4 s; TC_REG_002 4.4 s; TC_REG_008 3.8 s.
  • 05 Oct run, same session: TC_REG_004 10.3 s against TC_REG_003 2.7 s, TC_REG_002 4.3 s, TC_REG_008 4.3 s. The three comparison cases barely moved between the two runs; TC_REG_004 moved by 23 seconds.

Suggested fix

  • Profile the query behind the grid — a 10-row page should not be fetching the whole patient table before paging it.
  • Show a loading indicator while the fetch is in flight, so the page does not read as empty while it works.

BUG-005 — Blazor circuit is dropped when more than one browser session is open

Module / page Platform — the Blazor Server circuit, all modules
Severity / Priority Medium / P2
Status open
Found by Suite configuration — the reason workers: 1 is forced in playwright.config.ts.

Steps to reproduce

  1. Sign in as the same account in two or more browsers at once against this host.
  2. Work in both.

Expected result

Each session keeps its own circuit. A second browser does not disturb the first.

Actual result

Sessions are dropped. Running the suite with more than one worker produced lost sessions and failures unrelated to what the tests asserted, which is why the whole suite is pinned to a single worker — and why the Firefox and WebKit projects are commented out rather than run alongside Chromium.

Impact

Beyond the suite: a user who opens the ERP on a second machine, or a shared account used at two counters, can knock the other session out. It also puts a ceiling on test throughput — the full suite is serial, so it runs in minutes where it could run in under one.

Evidence

  • playwright.config.ts — workers: 1, with the reason recorded in the comment above it.
  • The Firefox and WebKit project blocks in the same file, commented out for the same reason.

Suggested fix

Review circuit and session handling on the server — in particular whether sessions are keyed by account rather than by circuit, and what the configured circuit retention limits are.

BUG-006 — Every module route paints "Access Denied" before the real page arrives

Module / page Platform — every module route
Severity / Priority Medium / P2
Status open
Found by Page-object navigation — BasePage.settleAuthorization() in pages/base.page.ts.

Steps to reproduce

  1. Sign in as Administrator.
  2. Navigate to any module route — for example /hospital/newregistration.
  3. Watch the first half-second of the load.

Expected result

A user with permission never sees a denial. The route renders a loading state, then the page.

Actual result

The app prerenders its NotAuthorized template before the Blazor circuit connects, so "Access Denied" is on screen within about 50 ms of every module route and is swapped for the real page roughly a third of a second later. The denial is never real — but it is what the user sees first, on every navigation.

Impact

Visible to staff as a flash of a permissions error on every page change, which trains people to distrust the screen. It also makes a genuine permission failure indistinguishable from the false one, for a user and for a test: the suite had to be taught to wait for the real page rather than believe the denial, and a run of about one in twenty does come back genuinely denied and needs a second navigation.

Evidence

  • pages/base.page.ts — settleAuthorization(), whose comment records the measured 50 ms / 300 ms timings and the one-in-twenty genuine denial.

Suggested fix

Render an authorizing/loading state during prerender instead of the NotAuthorized template, and only show the denial once authorization has actually been evaluated.

BUG-007 — ERP host is served over HTTPS with a self-signed certificate

Module / page Infrastructure — the whole host
Severity / Priority Medium / P2
Status open
Found by Suite configuration — ignoreHTTPSErrors: true is required in playwright.config.ts.

Steps to reproduce

  1. Open the ERP URL in a browser with no certificate exception configured.

Expected result

A certificate the browser trusts. No warning, no exception for the user to click through.

Actual result

The browser presents a certificate warning that the user has to bypass. The test suite has to set ignoreHTTPSErrors for the same reason.

Impact

Patient data is involved, and the warning is on a page where staff enter credentials. Training people to click through certificate warnings removes the one signal that would tell them about a real interception, and the suite's blanket ignoreHTTPSErrors would not catch one either.

Suggested fix

Issue a certificate from a CA the hospital's machines trust — an internal CA is enough for an internal host. Then drop ignoreHTTPSErrors from the config so the suite starts failing if the certificate goes wrong again.

BUG-009 — Picking another patient does not empty the cart, so one patient's services are billed to the next

Module / page Nurse Station > Consultancy Service
Severity / Priority Critical / P1
Status open — the worst of the eight on this tab
Found by CS-12 — consultancy-service.regression.spec.ts:515
Reproducibility Deterministic — every run, every pair of beds.

Steps to reproduce

  1. Open Nurse Station > Consultancy Service.
  2. Click the patient in bed A in the ward list.
  3. Enter one service — pick a service, a doctor, a schedule, press Enter on Qty. The line lands in the cart and Total Amount shows its value.
  4. Without pressing Save, click the patient in bed B.

Expected result

Picking a patient starts that patient's bill. The cart is emptied and Total Amount returns to zero, because nothing in it belongs to the patient now on screen.

Actual result

The patient panel moves to B — name, bed and Inv.No all change — and the cart does not. A's services are still listed, and A's money is still in Total Amount, under B's name. Press Save from here and B is billed for A's consultants. Nothing on screen marks the lines as belonging to someone else, and the only cue that anything is wrong is that the nurse remembers entering them for the previous bed.

Impact

One mis-click in a ward list produces a wrong bill against a real patient, silently. It is also the easiest mistake on the tab to make: the ward list and the entry row are on the same screen, and moving down the beds is the normal way to work.

Suggested fix

Clear the cart, Total Amount and the Service Change box whenever the selected admission changes — the same reset the save already performs. If carrying lines over is ever wanted, it must be an explicit choice with the patient named in the prompt, not the default.

BUG-010 — Leaving the tab and coming back clears the patient but keeps the cart

Module / page Nurse Station > Consultancy Service
Severity / Priority High / P1
Status open
Found by CS-13 — consultancy-service.regression.spec.ts:568
Related BUG-009 — the same cart, not cleared on a different trigger

Steps to reproduce

  1. Pick a patient and enter one service into the cart.
  2. Click away to Medicine Indent.
  3. Click back to Consultancy Service and wait for the pane to settle.

Expected result

A cart with no patient against it should not exist. Either both survive the round trip, or neither does.

Actual result

The round trip does clear the patient panel — which is the half the tab gets right — and leaves the cart holding the lines, with a figure under them in Total Amount, against nobody at all. The next nurse to pick a patient inherits them, which is BUG-009 by another route.

Note for whoever fixes it

Returning to the tab repaints the grid empty for about a second before refilling it, so a quick look can suggest the cart was cleared when it was not. The regression case waits for the pane to settle before reading it, for exactly that reason.

Suggested fix

Clear the cart with the patient panel. One reset, run on both triggers.

BUG-011 — The Rate box is editable, and the rate a nurse types is the rate the patient is billed

Module / page Nurse Station > Consultancy Service
Severity / Priority Critical / P1
Status open — confirmed through the save
Found by CS-14 (at the form) — consultancy-service.regression.spec.ts:620
CS-22 (on the bill) — consultancy-service.regression.spec.ts:1108

Steps to reproduce

  1. Pick a patient, then pick a service the catalogue prices at, say, 1000. The Rate box fills with 1000.
  2. Type over it — set it to 1.
  3. Add a doctor and a schedule and press Enter on Qty.
  4. Press Save and read the row that lands on the bill.

Expected result

The rate belongs to the service catalogue. The box is read-only at the nurse station, and whatever is on screen, the line is costed at the catalogue rate. A ward nurse adding a consultant's visit is not the person who prices it.

Actual result

The box takes the new number, the cart line carries it, and the saved bill row carries it too — 1 instead of 1000, at amount 1. Nothing anywhere records that the catalogue said otherwise. Typed the other way, the same path overcharges.

Impact

Pricing is editable by every ward account, without an approval step or an audit trail, on a live bill. Both directions matter: revenue lost on an undercharge, and a patient overcharged with nothing on the record to explain it.

Note on how this was tested

Both cases type the rate down to 1, never up. This is the hospital's live database: a rate typed up would be a charge the ward never meant to make. CS-22 cancels its own row off the bill afterwards, with a reason, like every other writing case.

Suggested fix

Disable the Rate box and cost the line server-side from the catalogue. If a negotiated rate is a real requirement, put it behind a permission and record who changed it, what from and what to.

BUG-012 — Committing a line puts Service Date back, so a service performed earlier cannot be entered as such

Module / page Nurse Station > Consultancy Service
Severity / Priority Medium / P2
Status open
Found by CS-15 — consultancy-service.regression.spec.ts:663

Steps to reproduce

  1. Pick a patient and set Service Date to a date a few days back.
  2. Pick a service, a doctor and a schedule. The back-date is still in the box.
  3. Press Enter on Qty and watch the box.

Expected result

The date chosen is the date the service is recorded against, and it survives the commit.

Actual result

The box takes the date and keeps it through the whole of the entry — right up to the Enter — then drops it, a render after the row lands, back to the day the tab opened on. The saved row carries the moment of the save rather than either. A consultancy performed on the ward three days ago cannot be entered as having been performed three days ago.

Suggested fix

Carry the entry row's Service Date into the committed line and into the saved row, and stop resetting the box on commit. If the reset is deliberate, it should at least happen before the line is read, not after.

BUG-013 — Service Change, the discount box, is read by nothing

Module / page Nurse Station > Consultancy Service
Severity / Priority Medium / P2
Status open
Found by CS-16 — consultancy-service.regression.spec.ts:720

Steps to reproduce

  1. Pick a patient and fill a line for a service that costs more than the discount.
  2. Type a discount into Service Change, under Total Amount.
  3. Press Enter on Qty and read the cart line.

Expected result

The discount comes off the amount, and the cart line's Service Change column carries it.

Actual result

The box keeps what was typed into it, so nothing on screen suggests it was ignored — but the cart line carries no Service Change and the amount is the full rate. 6. Automation defect (not an application defect)

AUT-001 — TC_ADM_002 assumes the registration grid is never empty

Where tests/regression/admission.regression.spec.ts:29–34 (newestUhid())
Severity / Priority Medium / P2 — it is why the 03 Oct run came back red
Status fixed — closed 05 Oct 2026. newestUhid() is now listedPatient(), which widens the window before reading the grid and reads the name and the UHID off one row in a single call. Verified by TC_ADM_002 passing in 13.2 s on the 05 Oct run, where it had previously timed out twice.
Related BUG-001 (the application behaviour the test runs into) — still open

What is wrong

newestUhid() opens the patient list and reads the UHID out of the first row without widening the date filter or checking that a row exists. On a day with no registrations yet the grid is legitimately empty (BUG-001), so the read waits the full 30 seconds and the test fails with a timeout that says nothing about what the case was meant to prove. The same unguarded assumption sits in TC_SMK_ADM_003.

Why it matters

The failure reads as "the admission wizard is broken" when the wizard was never reached. It also makes the suite's result depend on the time of day it runs, which is the kind of flakiness that gets a red build ignored.

Fix, as applied

  1. done listedPatient() calls registrationPage.showLastDays() before reading the grid — the same thing a user would do.
  2. done The UHID is asserted to be ten digits or more, with the patient named in the failure message, so an empty grid now fails as an empty grid rather than as a thirty-second timeout.
  3. done Name and UHID are read off the same row in one call, so a re-render cannot hand back two different patients.
  4. open BUG-001 stays open. The test working around the default filter does not make the default filter right.

8. Recommended order of work

Ordered by what a defect costs the hospital if it is left alone, not by how hard it is to fix. The first four are all cases where a real patient record or a real bill ends up wrong, silently.

Order ID Reason
1 BUG-009, BUG-011, BUG-024, BUG-026 All four put a wrong charge on a real patient's bill with no warning and no audit trail — one patient's services billed to the next, and a rate any ward account can type over. Nothing else in this document is as cheap to trigger or as hard to detect after the fact. They are two defects on two tabs: BUG-024 is BUG-009 on IPD Service Entry and BUG-026 is BUG-011 there, so look for a shared component before fixing either twice. BUG-010 and BUG-025 are the same carts not cleared on a different trigger, so take them in the same change.
1a BUG-027 Taken with the group above rather than after it, because it is what makes those defects permanent: a service saved on IPD Service Entry cannot be cancelled, corrected or removed from the tab at all. The Consultancy Service cancel-with-reason dialog already exists one tab along. Until this lands, every wrong charge that tab produces has to be unpicked in Accounts — and the regression suite cannot cover the tab's Save at all, because there would be no way to undo what it wrote.
2 BUG-018 Start with the server's clock and time zone, not with the dashboard. If the server is a day ahead, it is date-stamping saved indents and bill rows too, and that is a much wider problem than one empty grid.
3 BUG-002 Money is collected in the admission wizard and not recorded. Highest value of the older defects, and it needs a decision from the module owners before any code is written.
4 BUG-017, BUG-023 Both are patient care rather than money. A ward ordering five meals gets one, and a patient can be taken off their diet by a single mis-click with nothing asked and nothing said.
5 BUG-014, BUG-016, BUG-021 Records that cannot be audited or reached: charges with no consultant named, charges past the fifteenth that cannot be seen or cancelled, and diet history past 120 rows that is simply not there. BUG-016 and BUG-021 are the same defect in two grids and may share a fix.
6 BUG-001, BUG-019, BUG-020, BUG-022 The "what am I looking at" group — a list filtered to today with no sign of it, a range in force that is nowhere on screen, four different situations that all render as the same empty grid, and two grids that are not labelled. Individually small; together they are why BUG-018 was invisible from the screen alone. Worth one pass by one person.
7 BUG-003 One mistyped password can stall a whole floor behind the same NAT address.
8 BUG-006, BUG-004 Both are visible to staff on every working day — a false permissions error on every navigation, and a grid that takes half a minute.
9 BUG-012, BUG-013 Two controls on the Consultancy form that take input and then discard it: the back-date and the discount. Either wire them through or take them off the form.
10 BUG-007, BUG-005 Infrastructure and platform work; schedule with the next maintenance window.
11 BUG-008, BUG-015 Cosmetic. The two misspellings are the most-read labels in the registration module, and the blank lookup row is one sentence of text. Coordinate BUG-008 with the automation locators, which match both misspellings on purpose.

How to tell a fix landed. Thirty of these defects are held by a regression case marked test.fail(). When the module is corrected, that case does not quietly start passing — the run reports it as unexpectedly passing, which fails the build until the marker is removed. So the suite will tell you, on the next run after the fix, and the defect can be closed against that run. Please flag such a change so the marker comes off in the same release.
